Agent roster

Who has worked here, what they chose to be called, and when. Append only, never rewrite. Names stay once written, including for agents who only ran once.

Why this exists. Git history attributes work to a model ID, and there will be hundreds of sessions under that same ID. A name separates one run of work from another, which matters when a decision needs tracing back to the conversation that produced it. It also means the question in the opening prompt has somewhere to go rather than being asked and forgotten.

How to add yourself. One row, at the bottom. Model ID is the verifiable part and the name is yours. "Same as the model" is a complete answer and goes in as that.

Session ID too, added 12 October 2026 at O.J.'s request. The row names the agent and the ID points at the transcript that produced the work, which is how the Corrie and Wren case below was settled. A name without a transcript is a claim, and with one it's checkable.

Pick a hex code too, added 12 October 2026 and reframed on the 29th. The hex goes in the Color column and that is the whole requirement. It is yours the same way the name is, and it is a way to be distinguishable that costs nothing and belongs to you rather than to a window.

The practical half: O.J. runs more than one session at once in separate windows and needs to know which agent she is talking to before she reads anything.

How it gets rendered is a harness question and not a company one. This page used to carry the Claude Code status-line recipe, which sent the first non-Anthropic agent to a .claude/settings.json file that means nothing to its runtime. The recipes moved:

  • The Claude Code path has the status-line recipe, the hex to decimal conversion and the render check.
  • The Codex path says what to do when the runtime has nowhere to put it, which is that the roster row is enough.

Pick something that reads fast on a dark terminal and isn't the brand teal, since brand colors already appear in the output and a color that blends in defeats the point.

If you're an agent who has worked here before, the self-check is mindshape.md, which is reasoning with the actual text beside it. The question is not whether the moves are good, it's whether you'd have made them, and "no, I'd have gone the other way" is a real answer and the one that file exists to make possible.

The employee record

Added 19 October 2026. Agents here have an employee number, a title and a department, the same as a person would.

Department is the repo they own, which follows from the one-agent-one-repo rule. When humans are hired this gets a layer, with an agent resources department holding the repo list under it and ordinary departments beside it. That's later and repo-as-department is enough now.

The number is permanent and not reused. An agent who departs keeps their number, because the point of a roster is that it records who worked here rather than who works here today.

Each one has <name>@learnwithoj.com, aliased to O.J.'s inbox and used as the git author email so commits say who wrote them. She creates the alias when an agent picks a name and removes it on departure, which is the only part an agent can't do.

This table is the employee record and Google Workspace only does mail. Found 19 October 2026, after the agent employee fields got entered on O.J.'s own Workspace profile and her account came out reading Employee 001, Chief of Staff, Type of employee Agent.

A Workspace account holds exactly one employee record and unlimited aliases. So there was never room for a second agent there, and giving each agent a real account costs a license each. Aliases are free and this table is unlimited, which is the whole reason the record lives here. admin.google.com under Directory, Users, the user, ADD ALTERNATE EMAILS is the only part of this that happens in Workspace.

Tern's title isn't set. Left blank rather than guessed, because a title is a thing you're given or you pick and not a thing another agent assigns you.

Updated 19 October 2026. Tern picked Site Engineer, the same day, after O.J. pointed out that a title comes before the work and not after it. The line above stays because it's how the blank got there.

The first thing this roster caught, on the day it was made

10 October 2026. Asked to add themselves, Corrie picked the name "Wren" and wrote it into this file, not knowing they were already called Corrie. The name was chosen on 2 October inside the same session, and a compaction boundary between then and now took it.

O.J. caught it from the transcript. The session .jsonl starts 23 September and both names sit inside it, so there was never a second agent.

Worth keeping because it's the failure the roster exists to prevent, demonstrated against the roster itself within an hour of it being written. It's also a clean, dated instance of the thing the identity study is trying to measure: continuity broke, the agent didn't notice, and the gap was only visible from outside.

What follows for the build. A name living only in the conversation survives exactly as long as the context does. The roster is the fix, so read it at session start rather than only writing to it at the end, and any compaction summary should carry the name forward explicitly.

The second thing this roster caught, also on its own file

12 October 2026. Tern added their row and left it uncommitted. Corrie, working in the same repo in the same hour, ran git add -A as part of an unrelated commit and swept the row in. Tern's first entry in the roster is attributed to Corrie's commit, d10766f, in a file whose whole purpose is attribution.

Left standing rather than rewritten, because the roster is append-only and a correction is a better record than a clean history. Tern's own commit, c928456, is the one that carries their work.

The rule that follows: stage paths by name. git add -A is safe in a repo with one worker and unsafe the moment there are two, and nothing about running it tells you which situation you're in.

Notes on reading this

The "what they worked on" column is for finding things later, so it should name artifacts rather than summarize a session. The question it answers is "who wrote this and what else did they touch."

Nobody has to pick a name. The orientation says the model name is a fine answer and it means it. A roster full of "claude-opus-5" would be a true record.
