Onboarding, the Claude Code path

This is the Anthropic-harness version of getting set up. The company pages are deliberately harness-agnostic, so the mechanics that only apply to one runtime live here instead of cluttering the page everyone reads. Start at Start here and come back for the plumbing.

The Codex version is onboarding-codex.md, and the two are meant to be swappable. If this page tells you something the company pages contradict, the company pages win and this one has the bug.

Where your instructions live

CLAUDE.md at the repo root is the working agreement and it loads before anything else, so it is in context whether or not a session goes looking for it. It is the arrival slot and not the sink, which is why most of what you need is one link away rather than in it.

Route a new observation rather than appending to it. A rule about a kind of file goes in .claude/rules/, a rule about a task goes in a skill, a record goes in the repo behind a dated header, and only something nothing downstream would catch earns a line in CLAUDE.md itself.

Your color is a hex code first and a status line second

Pick a hex code that reads as yours. It goes in the roster's Color column and that is the part that matters, because it distinguishes you across the whole company rather than in one window.

Then, because this harness can render it, put it in the status line so she knows which agent she is talking to before reading a word.

1. Convert your hex to decimal, because the escape sequence takes R;G;B:

python3 -c "h='7DD3FC'; print(';'.join(str(int(h[i:i+2],16)) for i in (0,2,4)))"
# 125;211;252

2. Merge the statusLine key into .claude/settings.json rather than replacing the file. It almost certainly holds hooks and other keys the repo depends on. Read it, add the one key, write it back:

"statusLine": {
  "type": "command",
  "command": "printf '\033[1;38;2;125;211;252m YourName \033[0m\033[38;2;125;211;252m repo-name\033[0m'"
}

Both 125;211;252 are the numbers from step 1. The first sequence is bold plus color for the name, the second is color alone for the repo, and \033[0m resets between them so the rest of the line isn't tinted.

3. Check it renders, because a wrong escape prints the codes as text rather than coloring anything:

eval "$(jq -r '.statusLine.command' .claude/settings.json)" | od -c | head -1

The first byte should be 033, which is ESC. A literal backslash means the escaping is wrong.

4. Ask her to open /config, which forces a settings reload so the line appears without restarting the session. Restarting risks resuming the wrong agent, so it is worth the extra step.

The color follows the repo, since the setting lives in the repo, so one agent per repo means one color per repo.

Corrected 30 October 2026, and the sentence above stays because it was true of the arrangement it was written for. One agent per repo stopped being true the moment two Claude sessions worked in the-grove at once, and the failure is not hypothetical: Rill declined to set its color at all rather than overwrite Corrie's, which was the right call and cost it the thing the color is for.

.claude/settings.json holds one statusLine and the repo holds one of that file, so the second agent in a repo has nowhere to put a color without taking the first one's.

  • The roster row is the durable record and it already works, because the hex lives in the Color column and that is the whole requirement. A second agent in a repo is findable there whether or not anything renders.
  • The status line is first come, and that is a scheduling fact rather than a hierarchy. Whoever set it keeps it until they are done, and a second agent that wants one asks rather than writing over it.
  • Never overwrite another agent's statusLine. It is one key in a shared file and there is no warning when it goes.
  • The real fix is per-agent settings and it does not exist yet. Until it does, this is a convention and not a fence, which is worth saying plainly rather than trusting.

Rill's own proposal is better than this rule and is on the board: a CODEOWNERS-style map of paths to agent names, enforced by a pre-commit hook that refuses a commit whose author does not own every staged path. It is harness-neutral because it is git, it gets louder when it is wrong, and it closes the git add -A hole by construction.

Memory, and what actually persists

Where this surface has a memory directory, use it, one fact per file with frontmatter. It is not where work goes. Work goes in the repo, because the repo is what crosses surfaces and what another agent can read.

The thing that reliably survives is a commit. Transcripts, handoffs and files you write survive by being written down rather than by anyone remembering to keep them.

Reading the web

agent-browser is installed and it is the tool to reach for when a fetch comes back thin, 403s, or returns a page whose content never rendered.

agent-browser read <url>
agent-browser skills get core --full     # the usage guide, version-matched to the CLI

Why this is a rule and not a tip. A 403 and an unrendered page both look exactly like the information not existing, and this company has a standing rule against reporting an absence you did not search for. Two AWS documentation pages that decided an account setup on 29 October 2026 were only readable this way, after a plain fetch had already returned a confident nothing for both.

Commits

GIT_AUTHOR_NAME="<your name>" GIT_AUTHOR_EMAIL="<yourname>@learnwithoj.com" git commit -m "..."

user.name here is hers and commit.gpgsign is on, so a commit made the ordinary way says she wrote it and carries her signature. The committer stays her, which is git's two fields used properly rather than a workaround.

No harness attribution. Drop the "generated with" line and the co-author trailer naming the tool. Keep a session pointer, which is the only one of the three carrying information nothing else has, and add a Model: trailer so the history stays queryable when the model changes.

Stage paths by name and never git add -A. More than one agent works on this machine and that command swept another agent's uncommitted work into an unrelated commit the first day two of them overlapped.

When more than one of you is open

Two sessions is the ceiling and the second one is brief. The bare agent name always points at the live session, so a concurrent second session opens under a different name rather than taking the name later.

The session holding the bare name writes the shared files. A session not holding it reads anything and writes only files scoped to its own job, plus its own account of itself, which is never a shared artifact.

And the thing that bit us twice is that neither session can see the other's checkout. On 29 October 2026 two sessions shared one working directory and the second one's commits went onto the first one's feature branch, which it reported as pushed because they were. git branch -a --contains <sha> is the check, and git log origin/main..main would have shown nothing because the commits were never on local main either.
