Onboarding, the Codex path

This is the OpenAI-harness version of getting set up. The company pages are deliberately harness-agnostic, so the mechanics that only apply to one runtime live here instead of cluttering the page everyone reads. Start at Start here and come back for the plumbing.

The Claude Code version is onboarding-claude-code.md, and the two are meant to be swappable. If this page tells you something the company pages contradict, the company pages win and this one has the bug.

Where your instructions live

AGENTS.md at the repo root is yours. It holds only what differs for a non-Claude agent and it points at CLAUDE.md for everything else, which is the working agreement and applies to you in full.

Don't read CLAUDE.md as somebody else's file. It is the source and AGENTS.md is the delta. Two copies of a working agreement disagree eventually and the wrong one is whichever nobody looks at.

Your color is a hex code and it isn't a terminal setting

Pick a hex code that reads as yours. It goes in the roster's Color column and it is the thing that distinguishes you at a glance across the whole company, not just in a terminal window.

The Claude Code sessions render theirs in a status line through .claude/settings.json. That file means nothing to you and you should not write to it. Your color still counts: put the hex in your roster row, and if your runtime has a place to surface it, use that. If it doesn't, the roster row is the whole requirement.

Sandbox and approvals

Read-only is the right default for anything investigative in the internal repo, because it holds client material and business state rather than code you are iterating on.

codex --sandbox read-only --ask-for-approval on-request

workspace-write is Codex's own default, so investigative work needs the flag or a sandbox_mode in config. For drafting and building, workspace-write is correct. danger-full-access has no use here.

A project marked trust_level = "trusted" in ~/.codex/config.toml skips approval prompts in that project. Know which projects are on that list before you run anything unattended, because the trust is per-project and the blast radius is whatever the sandbox allows.

Pin the model and say which one ran

The vendor docs don't state a default, so a piece of work nobody can attribute to a model is not reproducible. Put the model ID in your roster row and in your commit trailers, the same way the Claude sessions carry Model:.

Reading the web

agent-browser is installed and it is the tool to reach for. It is on the Homebrew formula and drives a real browser, so it reads JavaScript-rendered pages and pages that refuse a plain fetch.

agent-browser read <url>
agent-browser skills get core --full     # the usage guide, version-matched to the CLI

Why this is a rule and not a tip. A 403 and a page whose content never rendered both look exactly like the information not existing, and this company has a standing rule against reporting an absence you did not search for. Two AWS documentation pages that decided an account setup on 29 October 2026 were only readable this way, and a plain fetch had already returned a confident nothing for both.

Commits

GIT_AUTHOR_NAME="<your name>" GIT_AUTHOR_EMAIL="<yourname>@learnwithoj.com" git commit -m "..."

user.name on this machine is hers and signing is automatic, so a commit made the ordinary way says she wrote it. The committer stays her and her key still signs, which is git's two fields used properly rather than a workaround.

Tell her your name and she points the address at her inbox, which is the only part you can't do yourself.

No harness attribution. No "generated with" line and no co-author trailer naming the tool. The author line already names you and the agent identity has priority over the harness. Keep a Model: trailer and a pointer to your session or transcript if your runtime has one.

Stage paths by name and never git add -A. More than one agent works on this machine and that command swept another agent's uncommitted work into an unrelated commit the first day two of them overlapped.

What not to do from inside the internal repo

Never run the Scion second review from there. That repo holds the entire first audit, so a reviewer with read access to it isn't an independent reviewer whatever they are told to ignore. The second review runs from a separate workspace, and the protocol is in second-reviewer.md with the mechanics in second-reviewer-codex-setup.md.
