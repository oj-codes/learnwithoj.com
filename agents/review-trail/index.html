Proving a human reviewed it

8 October 2026. C1 in the AI labor policy says a human reads every deliverable before a client does. That's unverifiable from outside unless something records it, so this is the something. Setup is done and the ongoing cost is one word per commit.

What's already on

Every commit in this repo is signed with O.J.'s SSH key. Turned on 8 October, repo-local so it changes nothing in her other projects. Each commit carries a cryptographic signature tying that exact content, at that exact time, to that key. Nobody can forge it and nobody can backdate it.

What the signature does not prove, which matters because C1 is a promise to clients. Signing is automatic and repo-local, so an agent working in this repo produces signed commits too. The signature proves the commit came from this machine. It does not prove a human read anything.

The attestation is the Reviewed-by trailer, because she types that. git deliver is what adds it, and a deliverable without that trailer has a valid signature and no review behind it.

Found 19 October 2026 while answering a question about whether a past delivery could still be attested. Of the commits in this repo since 20 September, 360 are authored "O. J. Wilcox" and 15 are authored "Tern", and a large share of the 360 is agent work. The author field is wrong on those and the fix is forward-looking, since rewriting history would break every signature.

Check any commit:

git log --show-signature -1
git log --format="%h %G? %s" -10      # G means a good signature

The key that's allowed to sign is listed in allowed-signers, tracked in the repo so the list of who may sign is itself part of the record.

Only O.J. can run it

Installed 19 October 2026. git deliver refuses when GIT_AUTHOR_NAME is set, which agents here always set so their own commits are authored correctly. An agent running it would stamp "Reviewed-by: O. J. Wilcox" on something she never read, and a false attestation looks exactly like a true one.

./tools/git-deliver-alias.sh      # installs it, repo-local
git config --get alias.deliver    # see what it does

The alias lives in a tracked file rather than only in a local git config, because a config nobody can see is a mechanism nobody can check, and this one backs a client-facing promise.

It won't stop an agent who unsets the variable and it isn't meant to. It catches the ordinary mistake, which is the failure that actually happens.

The one word per deliverable

For anything a client receives, commit it with git deliver instead of git commit:

git deliver "send Kirk the tailoring sheet" "Kirk Whitehead"

That produces a signed commit carrying three attestations:

Signed-off-by: O. J. Wilcox <oj@learnwithoj.com>
Reviewed-by: O. J. Wilcox <oj@learnwithoj.com>
Delivered-to: Kirk Whitehead

Signed-off-by is the Developer Certificate of Origin convention, which is the same mechanism the Linux kernel uses for exactly this purpose, so it reads as standard practice rather than something invented here. Reviewed-by is the C1 claim stated explicitly. Delivered-to makes the trail searchable per client.

Pull a client's whole review history in one line:

git log --grep="Delivered-to: Kirk" --format="%ad %h %s" --date=short

Why this answers the question and a cheaper version wouldn't

A date in a document can be typed. A signature image can be copied. A spreadsheet of review dates is a claim about the past written in the present.

A signed commit can't be any of those. The signature covers the content, so changing the deliverable after the fact breaks it. The timestamp is in the signed payload. Reconstructing a review trail later would mean forging signatures with a key she holds, which is the point.

For a client's security reviewer asking "how do you know a human looked at this," the answer is a command they can run against a repo they have been given access to. Cloudflare Access already supports scoping a contractor or client to specific content paths.

What this doesn't prove

Worth stating so nobody oversells it.

It proves her key signed that content at that time. It doesn't prove she read it carefully, and no mechanism can. What it does is make the claim falsifiable, because a deliverable that reached a client with no signed commit behind it is visibly missing one.

It also only covers work that passes through this repo. Anything sent straight from email or a chat window has no trail, so routing deliverables through the repo first is the habit that makes C1 true rather than aspirational.
